# Jugador 2 — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir el mod `jugador2` para Minecraft 1.21.1 con Forge 52.1.0: un jugador real del servidor controlado por una IA integrada, con pruebas unitarias, un escenario automático en juego y un artefacto de GitHub Actions.

**Architecture:** Proyecto Gradle separado en `jugador2/`. La lógica pura (nombres, órdenes, prioridades, A*, ciclo de vida) se prueba con JUnit. Lo que toca Minecraft se valida con un escenario que corre en un servidor de desarrollo dentro de CI y termina con `RESULT PASS` o `RESULT FAIL`.

**Tech Stack:** Java 21, ForgeGradle 7 (`[7.0.3,8)`), Minecraft 1.21.1, Forge 52.1.0, JUnit 5.14.4, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-15-jugador2-design.md`

## Review Focus

1. Orden con bloque o jugador inexistente (`mina xyz`, `sigue a Nadie`, o un jugador que se desconecta) → aviso en el chat y la orden termina; nunca excepción ni orden colgada. Tests: `OrderParserTest.unknownBlockNameIsKeptAsText` (Tarea 4) y `OrderStateTest.missingTargetFailsOrder` (Tarea 12).
2. Dos `spawn` seguidos, o reinicio con el NPC muerto a mitad de la espera → no duplica el NPC y reaparece con el tiempo que le quedaba. Tests: `NpcLifecycleTest.activateTwiceKeepsState` y `NpcLifecycleTest.restoreWhileDeadKeepsRemainingTicks` (Tarea 8).
3. Objetivo en el aire o encerrado → `findPath` devuelve `null` dentro del límite de nodos, sin colgar el servidor. Test: `NpcNavigatorTest.floatingGoalReturnsNull` (Tarea 5).
4. Excepción dentro de la IA → el NPC queda suspendido 200 ticks y el servidor sigue. Tests: `NpcSuspensionTest.suspendedForExactly200Ticks` (Tarea 8) y la envoltura en `NpcManager` (Tarea 12).
5. Un jugador escribe un nombre parecido (`Ryvexito, ven`) → el NPC no obedece. Test: `OrderParserTest.similarNameDoesNotTrigger` (Tarea 4).

## Decisiones del plan

Lo que el spec no fijaba y este plan sí:

- **Carbón:** se recolecta si hay menos de 16.
- **Inventario lleno:** `STORE` se evalúa antes que la recolección. Así el NPC deja de recoger cuando el inventario está casi lleno, como pide la sección 9 del spec, aunque la lista de la sección 7.1 ponga el guardado después.
- **Nombres de tareas:** `Survive` del spec se divide en `FleeTask` y `EatTask`, y el paquete es `ai/tasks/` (plural). No cambia el comportamiento.
- **Escenario:** los pasos 1–7 del spec se amplían con los pasos 8–13: orden `ven` (8), defensa (9), huida (10), recolección de madera (11), crafteo (12) y cofre (13). Los pasos 8–13 son pruebas adicionales de las secciones 4 y 7 del spec.
- **Activación del escenario:** `-Djugador2.selftest=true` o la variable de entorno `JUGADOR2_SELFTEST=1`. CI usa la variable porque no depende de cómo cada versión de ForgeGradle pasa propiedades de JVM.
- **Cerebro apagado durante los pasos 1–7:** el escenario controla al NPC. El cerebro se activa al empezar el paso 8.
- **Retirada del NPC muerto:** se quita de la lista en el tick siguiente a la muerte, no dentro del evento, para no interferir con el drop de objetos.
- **Movimiento:** se fijan los campos de entrada de `LivingEntity` (`xxa`, `zza`) y se deja que `travel` aplique gravedad y colisiones, como en los mobs.
- **Sin prueba automática:** cama (`SleepTask`) y chat real. Se verifican a mano en el punto 11.3 del spec.

- [ ] **Paso 1: Escenario primero.** `start` construye una plataforma de piedra de 20×20 en una zona despejada con aire encima, fija `doMobSpawning=false` y la dificultad en fácil.
